# infra/audit 的设计

本页写这个组件为什么这样设计：术语、拥有的数据、规则、命令、实现状态与未决问题。写给要修改它的人与 AI。怎样使用、部署与配置在 `BRICKKIT.md`；代码在哪、怎样构建与测试、设计取舍在 `AGENTS.md`；审计组件的义务在本仓库 `contract/README.md`；规则全文在装配项目的协议 03（转运与回执）、协议 14（纪元与分叉点）、协议 15（证据存储）。

## 边界

集中保存业务审计记录，给来源回执，告诉来源记录备份到了哪里，并提供受授权保护的查询；兼任独立证据存储（协议 15）。所有正式部署都需要它（必需审计，D28），装配检查阻止缺少它的正式组合。

| 不在这里 | 归谁 |
| --- | --- |
| 审计记录的产生、本地暂存与转运 | 各组件的 SDK（`rt.Audit`），按协议 03 |
| 什么操作要审计 | 各组件的资源定义（操作的 `Audit`） |
| 备份本身 | 部署的备份（协议 15）；本组件只登记“已备份到哪里” |

## 术语

| 业务叫法 | 定义 | 代码标识符 |
| --- | --- | --- |
| 审计记录 | 来源产生的一条规范字节的记录，带来源、产生序号与摘要 | `be.audit.record`、`Wire` |
| 回执 | 记录持久之后给来源的确认：审计库的纪元、存储序号、来源链的摘要 | `Receipt` |
| 来源链 | 按来源、按存储顺序累积的摘要 | 链摘要 |
| 已备份水位 | 已进入审计库备份的最大存储序号；来源只删除被它覆盖的本地行 | `Watermark` |
| 纪元与分叉点 | 审计库每次恢复或切换是一个新纪元；旧纪元的最后序号是分叉点 | 纪元历史 |
| 独立证据 | 恢复时不能丢的记录（安全记录变更、销毁与擦除、对外命令终态），与审计分开存放 | 协议 15 |

## 拥有的数据

集中保存的审计记录与回执、存储计数（每次接收在这一行上加锁、连续编号）、纪元历史（随库一起恢复）、来源与它们的链、备份登记、证据存储。表在 `audit/migrations/`。审计记录是一个数据类别 `infra.audit.records`（装配项目协议 11，决定 A158）：主键 `(source, id)` 用 `rkey` 列（`source/id`，与记录一起写入、约束它等于两列）作类别的主键；按来源与接收月分组，接收满一年封存、转层、释放在线行，保留期由部署给（`TIERING_RETENTION_INFRA_AUDIT_RECORDS`，协议 03 的保留按类别、地区与客户要求定），没给的从不删除。

## 规则

- 回执只在记录持久之后给出；来源凭回执与已备份水位删除本地行，所以不能“先回答、后写入”。
- 记录先按 schema、规范形式与摘要校验，再按（来源，记录身份）查重：不合格的字节不能凭旧身份拿到“已收到”。
- 同一来源的接收串行（存储计数行的锁），链摘要的顺序就是存储的顺序。
- 来源的产生序号出现空位只告警，记录照常保存：补发由来源负责。
- 纪元变化时，旧纪元的最后序号作为分叉点写进纪元历史（协议 14）。
- 审计组件不知道有过备份时，水位答 0，来源一行也不删。
- 审计查询本身受授权；证据只追加，存储不随部署备份回退（设计，协议 15）。
- 已释放在线行的记录再到达时，接收在事务之前从归档读出它，答原来的回执（重复或冲突照旧）；事务里不读对象存储。
- 链校验从每个来源第一条在线记录接着算：它之前的记录已封存、由单元的摘要保护（A158）；来源没有已释放的记录时照旧从头算。来源的记录全部已释放、之后没有新记录时，链头对照归档里最新一个单元中存储位置最后的那条记录的链值（在事务外读归档）；那个单元已到保留期销毁时无从对照，不算断。
- 恢复用的列表（`RecordService.List`）只答在线的记录：要的范围碰到已离开在线表的记录时答 `QUERY_NOT_COMPLETABLE`，不答一部分（恢复的范围是天，记录在线一年）。
- 法律保全挡住保留期删除（协议 03 的 AU17）：保全与删除批准经 SDK 的标准路由，操作是 `infra.audit.record.hold` 与 `infra.audit.record.approve_destruction`。

## 命令与查询

| 命令或查询 | 面 | 操作 |
| --- | --- | --- |
| 接收转运（幂等，返回回执） | 系统面 `be.audit.v3.IntakeService/Submit` | `infra.audit.intake.submit` |
| 已备份水位 | 系统面 `IntakeService/Watermark` | `infra.audit.intake.watermark` |
| 查询记录（按来源、操作，从新到旧，最多 500 条） | 用户面 `GET /api/audit/records` | `infra.audit.record.read` |
| 查询全部历史（`history=true`：在线与归档的记录，时限内完整，否则答 202 与导出） | 用户面 `GET /api/audit/records?history=true` | `infra.audit.record.read` |
| 法律保全、删除批准、导出状态（SDK 的标准路由） | 用户面 `/be/tiering/infra.audit.records/…` | `infra.audit.record.hold`、`infra.audit.record.approve_destruction`、`infra.audit.record.read` |

本组件发布的契约在 `contract/`（单独的模块）。

## 依赖

数据库、身份成员、授权成员（只为查询）。接收记录不调用任何组件。本组件自己的审计记录也经 `AUDIT_GRPC_URL` 走同一个入口。

## 未决问题

- 备份完成怎样登记、由谁登记（协议 15 的实现）。
- 独立证据与审计记录的存储分开到什么程度（同库不同表，还是另一个存储）。
- 一条记录在保留期满被删除之后又到达（来源多年后补发）时，写屏障拒绝它，来源一直重发；现实中来源不会保留这么久，先记在这里。
- 审计记录中的个人信息怎样假名化（协议 03 的未决项）：现在审计记录没有可擦除的列，事实本身不删。
- 证据存储（`be_evidence_*` 表）不转层。
